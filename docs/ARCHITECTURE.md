# Решения архитектуры

**Русский** · [English](ARCHITECTURE.en.md)

## Граница подтверждения

API возвращает 202 после commit Event+Delivery+DeliveryRun+Outbox. Уникальность
(project, source, external ID) и хеш канонического JSON различают повтор и
конфликт. Отказ брокера не отменяет уже принятое событие. Подтверждение
получателем записывается как `accepted`, прикладное состояние не угадывается.

Publisher арендует строки outbox, отправляет persistent-сообщение с mandatory и
publisher confirms, затем отмечает публикацию. Неизвестный результат означает
повтор. Worker принимает только версионированные небольшие ссылки на задания;
данные загружает из PostgreSQL. Задание с устаревшим run/generation игнорируется.
Отклонённые схемы попадают в отдельную очередь `eventhub.invalid` без payload.

Worker выделяет короткую транзакцию на claim, отпускает её до HTTP и отдельной
транзакцией сохраняет результат. Токен аренды ограждает от позднего ответа.
Scheduler восстанавливает истёкшие аренды, назначает наступившие повторы и
повторно публикует готовые задания, оставшиеся без обработки. Ни сеть, ни сон
не удерживают транзакцию бронирования/доставки.

## Конкуренция и пределы

Состояние проекта/SSE sequence меняется под блокировкой строки Project; глобальный
короткий advisory lock сериализует выделение квот работникам. Долгие операции
между проектами не разделяют эту блокировку. Пакеты outbox чередуются между
проектами. По умолчанию одновременно выделяется до 16 HTTP-заданий, до 8 на проект,
до 2 на получателя. У HTTP таймаут 10 секунд, аренда 60 секунд; до 5 попыток и
общий срок 24 часа. Перенос по квоте не расходует попытку. Прикладной приёмник B
сериализует обработку одного namespace и хранит receipt+эффект одной транзакцией.

## Полные снимки вместо команд

Версия относится к снимку одного booking UUID, а не ко времени получения.
B применяет только более новую версию; тот же event ID/хеш распознаёт как повтор.
Равная версия с другим статусом вызывает конфликт. Этот подход нельзя механически
применить к команде «увеличить баланс»: у неё другой контракт.

A намеренно применяет каждый новый сетевой вызов в порядке прихода. Это контрольный
дефект. Его технический Invocation ledger позволяет восстановить прерванный runner
после commit, но не устраняет намеренные повторы event ID в новом invocation.
Иначе лаборатория скрывала бы саму демонстрируемую ошибку.

## Воспроизводимость

Сценарий сохраняет конверты, порядок, ограниченный список сбоев, seed, виртуальное
начальное время, ожидания для A/B и checksum. Runner создаёт отдельный UUID namespace
для каждого запуска. Детерминированный invocation ID позволяет узнать, был ли
конкретный вызов уже зафиксирован. Версия файла приёмника проверяется до продолжения;
при изменении версиями не смешиваются результаты. Отмена проверяется между шагами.

Сравниваются статус, последняя версия и число повторных эффектов. Нормализованный
итог исключает случайный run ID и длительность сети. Реальные таймауты и время
выполнения сохраняются отдельно; побитовая воспроизводимость сети не обещается.
Сценарий поддерживает один source+subject и не восстанавливает произвольный сервис.

## Безопасность локального стенда

| Граница | Реализация |
| --- | --- |
| Вход | Случайный owner key, хеш с pepper, префикс поиска, constant-time compare |
| Права | Project + scopes + source; роли ограничивают выдаваемые scopes; отзыв и срок |
| Браузер | HttpOnly/SameSite cookie, origin+CSRF, CSP, текстовый вывод, без localStorage ключей |
| Получатели | Только lab-a/lab-b; адреса не поступают из JSON; HMAC связывает проект/цель/тело/время |
| Replay | Только подготовленные обработчики и fault types, без пользовательского кода |
| Базы | Отдельные runtime-роли и базы; migrations role не передаётся runtime |
| Контейнеры | Non-root UID/GID владельца, readonly, tmpfs, cap_drop, ограничения памяти; без docker.sock |
| Сеть | Core/lab internal; наружу опубликован только API на 127.0.0.1:8100 |
| Секреты | .env/.local закрыты; Docker build исключает их; тела/ключи не логируются |

Лабораторные контейнеры не имеют внешнего сетевого выхода, доступа своими
учётными данными к основной базе или основных секретов. Они находятся в общей
внутренней сети с контроллером; это не отдельная машина и не защита от kernel escape.
API имеет отдельную front-сеть для loopback-порта. Core — доверенные процессы;
их runtime-ключи достаточны для операций своего назначения.

В демонстрационном HTTP-профиле secure cookie выключена и нет MFA/SSO.
APP_MODE, отличный от demo, отвергается. Публичный доступ требует отдельной
архитектуры TLS/edge limits/identity/egress и проверки внешнего развёртывания.

## Отличия от первоначального плана

Модули объединены по ответственностям в `app/services/worker/replay/security`,
вместо большого количества однофайловых сервисов. Настоящие PostgreSQL, брокер и
подготовленные HTTP-получатели сохранены. Вместо отдельного Prometheus/Grafana
сервера есть защищённый `/v1/metrics` и Collector с debug exporter; установка
дополнительных систем наблюдения не выполнялась. Фильтрация событий — общий поиск
по ID/source/subject с подписанным курсором. Свободный визуальный редактор графа
сценариев не нужен: доступны готовые сценарии, capture и проверяемый JSON import.
Существующий сайт подключён отдельным outbox-адаптером, по умолчанию выключенным.
