# Демонстрация проекта

**Русский** · [English](DEMO.en.md)

## Сценарий на 3–5 минут

1. Открыть панель и показать различие HTTP accepted / проверенного результата.
2. Запустить «Отменённая запись снова активна»: ревизии 1 → 3 → 2 → 2.
3. Открыть отчёт. A вернул старое подтверждение и повторил эффект; B сохранил
   отмену версии 3 и распознал повтор. Показать правила и реальные наблюдения.
4. Запустить «Ответ потерян после сохранения»: транзакция завершилась, но отправитель
   получил timeout. Сетевой повтор не должен дублировать уже выполненное действие.
5. В журнале открыть событие → создать сценарий по объекту. Показать обезличенный
   JSON export/import с контрольной суммой и новый изолированный запуск.
6. При техническом обсуждении открыть Event+Outbox транзакцию,
   [тесты восстановления](../tests/test_delivery.py) и [отчёт проверок](VERIFICATION.md).

Уникальная часть проекта — воспроизводимый инцидент, наблюдаемое состояние
получателей и проверка исправления на одном входе. Число технологий само по себе
не является результатом.

## Для резюме

**EventHub ReplayLab — доставка событий и воспроизведение инцидентов.**
Python, FastAPI, PostgreSQL, RabbitMQ, SQLAlchemy/Alembic, Docker, OpenTelemetry.
[Репозиторий](https://github.com/Sasambatra/eventhub-replaylab).

Разработал платформу с транзакционным outbox, обработкой повторов, арендой заданий
и восстановлением после сбоев. Реализовал изолированную A/B-лабораторию:
перестановка сообщений и потеря ответа после commit воспроизводят дефект контрольного
обработчика, а проверки состояния подтверждают исправление. 42 автоматических
теста используют реальные PostgreSQL/RabbitMQ/HTTP и Hypothesis; отдельно
проверены восстановление трёх баз и интеграция с Django через outbox-адаптер.

## Что объяснить на техническом интервью

- Где проходит commit и почему приём API не зависит от доступности брокера.
- Почему транспортный повтор сохраняет event ID и как обнаруживается конфликт.
- Чем snapshot revision отличается от времени получения сообщения.
- Почему receipt и прикладное изменение B сохраняются одной транзакцией.
- Как lease token не даёт старому работнику перезаписать новое состояние.
- Почему HTTP 200 не доказывает business verified.
- Какие допущения ограничивают проверку A/B и как проверялось восстановление.

Проект не заявляет коммерческую эксплуатацию, production-нагрузку или работу
команды. Локальные измерения приводятся только с условиями в VERIFICATION.md.
Тесты подтверждают поведение реализации, а не процент покрытия строк или
автоматическое владение каждым инструментом.
