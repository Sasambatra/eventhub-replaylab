# Локальная эксплуатация

Команды выполняются в корне клонированного `eventhub-replaylab`.
Для демонстрации достаточно Python 3.10+ и Docker; `.venv` требуется только
для native-разработки/проверок. Сайт бронирования работает отдельно.

## Запуск и остановка

```bash
python3 scripts/stack.py start
python3 scripts/stack.py status
python3 scripts/stack.py logs
python3 scripts/stack.py stop
```

Первое слово — Python этого проекта; затем путь к скрипту и действие.
`start` последовательно собирает образ, поднимает PostgreSQL/RabbitMQ, выполняет
миграции и повторяемый bootstrap, запускает приложение и ждёт готовности API.
`stop` сохраняет тома. `status/logs` читают состояние и последние безопасные журналы.
Не выполняйте `docker compose down --volumes` для основного стенда: это удалит его данные.

[Панель](http://127.0.0.1:8100/) · [API](http://127.0.0.1:8100/docs) ·
[Ready](http://127.0.0.1:8100/health/ready).

Owner access: `.local/owner-access.txt`, поле `key`. Открыть файл можно через VS Code
и скопировать значение в форму. В чат/скриншоты/публикацию его не добавлять.
Если файл потерян, а база осталась, bootstrap не выводит существующий секрет:
потребуется отдельная локальная процедура восстановления владельца. Не удаляйте
базу ради замены ключа. Истёкший или отозванный ключ немедленно лишает доступа и
связанные браузерные сессии.

## Разработка и проверки

`test_infra.py` включает `compose.dev.yaml`, открывает loopback 55432/5673,
создаёт тестовый vhost и применяет миграции только `*_test`. Pytest запускает
тестовые receiver-процессы на 8211/8212 и останавливает их после проверки.
Запуск останавливается при занятых портах/недоступных зависимостях; основной проект
и его таблицы не очищаются. `scripts/local_stack.py` — дополнительный native режим
для разработки; одновременно с контейнерным API на тех же портах его не запускают.
Основной способ использования — `stack.py start`.

```bash
.venv/bin/python scripts/test_infra.py
bash scripts/check.sh
python3 scripts/stack.py start
```

Последняя команда возвращает обычную топологию без открытых портов базы/брокера.
Изменения Python требуют пересборки/перезапуска контейнеров; `stack.py start`
делает это. Пользовательские данные в томах сохраняются.

## Диагностика

- `/health/live` означает, что API отвечает. `/health/ready` проверяет основную БД;
  готовность к приёму событий не зависит от доступности брокера.
- `/v1/metrics` требует ключ/сессию и показывает только свой проект: непереданный
  outbox, возраст ожидающей доставки и количество состояний. Это текущие gauges.
- Журнал событий/попыток помогает отличить сетевую ошибку, исчерпание бюджета и
  отключённую цель. 200 получателя не означает business verified.
- При недоступном брокере publisher переподключается; события остаются в БД.
  После восстановления они должны перейти из ready в accepted либо в явно
  объяснённое конечное состояние. Не удаляйте outbox для «починки очереди».
- `docker compose logs otel` показывает приём трасс Collector. Долговременное
  хранилище трасс не установлено. HTTP access logs выключены, ключи/тела не пишутся.

## Хранение

Очистка запускается явно; периодическое системное расписание не установлено:

```bash
# Вызов внутри запущенного API-контейнера использует внутренние адреса БД/лаборатории.
sudo docker compose exec -T api python -m eventhub cleanup
```

В текущем WSL вместо `sudo docker` доступен установленный Docker через root Ubuntu;
обычный `sudo` может запросить ваш локальный пароль. Пароль не передают в чат.

По умолчанию payload хранится 7 дней и очищается только у событий без активных
доставок. ID/source/hash остаются как защита от повторов. Повторная доставка после
истечения payload даёт 410. Через 30 дней удаляются старые попытки, опубликованные
outbox конечных доставок, SSE changes и аудит; просроченные сессии/счётчики тоже
очищаются. Данные изолированных завершённых replay удаляются в обеих лабораториях,
а report помечается retention_expired. Сохраняются IDs, delivery/run metadata,
ключи дедупликации и определения сценариев. Это не безграничный архив всех тел.

## Резервирование и проверка восстановления

```bash
.venv/bin/python scripts/backup.py create
.venv/bin/python scripts/backup.py verify --path .local/backups/ИМЯ_КОПИИ
# Или создание и проверка одним действием:
.venv/bin/python scripts/backup.py drill
```

Копирование кратко останавливает **только работающие процессы этого проекта**,
сохраняет три custom-format дампа, SHA-256, количества строк и приватную конфигурацию,
затем возвращает процессы даже при ошибке. Так данные core/receivers согласованы
в одной остановке записи. Папка owner-only. Копии не зашифрованы: для переноса
нужно защищённое хранилище. Хранить вне единственного диска и периодически проверять.

`verify` сначала проверяет все хеши, затем создаёт случайные базы с префиксом
`eventhub_restorecheck_`, выполняет pg_restore с остановкой на ошибке, проверяет
количество строк каждой таблицы и удаляет временные базы. Основные базы не
перезаписываются. Приватный результат: `.local/reports/restore-drill.json`.

Восстановление основного стенда — отдельная операция с остановкой записи,
сохранением текущих томов, проверкой версий PostgreSQL/миграций и возвратом
`private.env` в `.env`. Проект намеренно не содержит команды, которая без проверки
перезаписывает действующие базы. После восстановления сначала изолированная
проверка и оба replay, затем возврат API. Runtime-ключи/pepper/Fernet key должны
соответствовать копии; смена паролей PostgreSQL потребует изменения ролей.

## Ограничения платформы

При выключенном компьютере Docker/WSL приложение недоступно. При следующем
запуске WSL нужен работающий Docker daemon; контейнеры имеют restart policy.
Адрес 127.0.0.1 доступен на этом компьютере. Это не публичная ссылка для работодателя.
Внешний хостинг не настроен. [Публичный репозиторий](https://github.com/Sasambatra/eventhub-replaylab)
содержит исходники; он не является работающим публичным сервером.
